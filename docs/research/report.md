# Turn your own session logs into nerf verdicts

The simplest fair design is a stdlib-only Python script, shipped as one skill in one GitHub repo for both Claude Code and Codex. The script reads the local JSONL transcripts that both CLIs already write. It scores **sessions, not days**, with deterministic signals first and a small, blinded LLM judge only on flagged events. It compares a fixed baseline window with a recent window inside the same "regime" (same model ID, CLI version, effort, and instruction-file hash). It then gives one of five verdicts: "better", "no change", "slightly worse", "clearly worse", or "not enough data yet". The gap in the market is real. Public trackers run fixed synthetic benchmarks at about 50 tasks per day, and the only proven session-log analysis is a one-off forensic study by AMD's Stella Laurenzo. That study used 6,852 sessions and found the March 2026 Claude Code regression before Anthropic admitted it ([The Register](https://www.theregister.com/2026/04/06/anthropic_claude_code_dumber_lazier_amd_ai_director/)). The hard limit is statistics, not engineering. A single user with 5 to 50 tasks per day can detect only drops of about **10 points or more on a weekly-to-monthly window**. The tool must say this plainly and must treat "not enough data" as a normal result. Three facts shape every design decision: real nerfs are usually harness or serving bugs, not weight swaps; they hit a sticky subset of users; and the user's own workload changes more than the model does.

## Real nerfs are harness and serving bugs that hit some users only

Vendor postmortems confirm that degradation is real, but its cause is almost never a quiet model swap. In August and September 2025, Anthropic had three overlapping infrastructure bugs. A context-window routing error sent up to **16% of Sonnet 4 requests** to the wrong servers at its peak, and about **30% of Claude Code users** had at least one misrouted message. The routing was "sticky", so an affected user stayed affected ([Anthropic postmortem](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues)). A TPU misconfiguration also put wrong tokens, such as Thai characters and syntax errors, into output. Anthropic said that its evals "simply didn't capture the degradation users were reporting", partly because Claude often recovers from isolated mistakes ([Anthropic postmortem](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues)). The same postmortem states that Anthropic never reduces model quality because of demand, time of day, or server load.

The March to April 2026 incident came from the harness, not the model. Anthropic lowered the Claude Code default reasoning effort from high to medium on 2026-03-04. A caching bug from 2026-03-26 cleared prior reasoning on every turn, and a verbosity limit in the system prompt from 2026-04-16 cost 3% on one eval. Anthropic said that "the API was not impacted" ([Anthropic April 23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem); [InfoQ](https://www.infoq.com/news/2026/05/anthropic-claude-code-postmortem/)). Each change "affected a different slice of traffic on a different schedule". OpenAI shows the same pattern. Its GPT-4o sycophancy update in April 2025 came from too much weight on short-term thumbs-up feedback ([OpenAI](https://openai.com/index/expanding-on-sycophancy/)). In the "lazy GPT-4" case, OpenAI said that it had not changed the model, but "only a subset of prompts may be degraded" ([Search Engine Roundtable](https://www.seroundtable.com/openai-chatgpt-gpt-4-getting-lazier-36529.html)).

These facts have three design results. First, the tool must measure through the real harness, because an API-only tracker would have missed the 2026 incident completely. Second, it must split every metric by CLI version and by model ID, because the cause can be in either layer. Third, per-user measurement is more correct than a global average, because sticky partial bugs give "it's nerfed" and "works fine for me" at the same time. Perception effects also exist. The best-known "GPT-4 got worse" paper reported a fall from 84% to 51% on prime identification ([Chen et al.](https://ar5iv.labs.arxiv.org/html/2307.09009)), but Narayanan and Kapoor showed that this was mostly a change in default answer preference, not lost reasoning ([AI Snake Oil](https://www.normaltech.ai/p/is-gpt-4-getting-worse-over-time)). No peer-reviewed study measures a "honeymoon effect" for LLM quality. The tool must therefore test perception effects as hypotheses, not assume them.

## Public trackers measure benchmarks, and nobody measures your own work

Existing trackers fall into three families, and none uses the user's own tasks. Marginlab runs the real Claude Code CLI every day on **50 SWE-Bench-Pro tasks**. Its significance thresholds are **±12.8 points daily, ±4.7 weekly, and ±2.3 monthly**, and its verdict is plain p < 0.05 against a baseline with no equivalence bound ([Marginlab](https://marginlab.ai/trackers/claude-code/)). AIStupidLevel re-runs a fixed set of models through vendor APIs. It uses Page-Hinkley change-point detection, but its coding suite has only 7 Python tasks, and an API-only design cannot see harness bugs ([AIStupidLevel methodology](https://aistupidlevel.info/methodology)). IsItNerfed.org combines a "Smarter / Same / Nerfed" vote with a private unit-tested challenge set and 34 Aider Polyglot exercises. Its About page gives no sample sizes and no statistical test ([IsItNerfed about](https://isitnerfed.org/about)). Votes are open to social contagion, and the OpenAI sycophancy postmortem shows that user-rating signals can push quality in the wrong direction.

The closest prior art is session-log forensics. Laurenzo's analysis used 6,852 session JSONL files, 17,871 thinking blocks, and 234,760 tool calls from one consistent work environment. It found that median thinking length fell by about **73%**, that files read before an edit fell from **6.6 to 2.0**, and that stop-hook violations rose from 0 to about 10 per day ([The Register](https://www.theregister.com/2026/04/06/anthropic_claude_code_dumber_lazier_amd_ai_director/); [lilting.ch](https://lilting.ch/en/articles/claude-code-quality-regression-thinking-redaction)). The open-source `lucemia/claude-session-analyzer` repeats this method on local logs ([GitHub](https://github.com/lucemia/claude-session-analyzer)). These are one-off scripts with no confounder controls, no statistical verdict, and no Codex support. Usage tools such as ccusage ([GitHub](https://github.com/ryoppippi/ccusage)), sniffly ([GitHub](https://github.com/chiphuyen/sniffly)), and claude-code-log ([GitHub](https://github.com/daaain/claude-code-log)) already parse the formats, but they report cost and activity, not quality drift. Anthropic's built-in `/insights` command writes a local 30-day HTML workflow report ([MindStudio](https://www.mindstudio.ai/blog/claude-code-insights-command-workflow-audit)). So the open space is narrow but clear: a continuous, per-user, confounder-aware drift verdict from real sessions, across both CLIs.

One warning from the Laurenzo case is important. Thinking-length metrics are confounded, because thinking redaction and display changes alter what the logs record. The April 2026 postmortem says that a thinking-display change hid the cache bug in most CLI sessions ([Anthropic April 23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem)). A log-based detector that does not track format changes will report false nerfs.

## Both CLIs already log enough to separate model, harness, and user

Claude Code writes one append-only JSONL file per session at `<config dir>/projects/<sanitized-cwd>/<sessionId>.jsonl`, with sub-agent transcripts in a `subagents/` folder ([ghinda](https://allaboutcoding.ghinda.com/where-ai-coding-clis-store-session-logs/)). Local inspection of 512 files from CLI versions 2.1.260 to 2.1.288 showed the fields that matter. Every message line carries `version` (the CLI version), `timestamp`, `cwd`, `gitBranch`, and `isSidechain`. Every assistant line carries `message.model`, full `message.usage`, `stop_reason`, and the harness fields `effort` and `perTurnEffort`. Tool results carry `is_error`, Edit results carry `userModified`, and user text contains the literal interrupt marker `[Request interrupted by user]`. System lines record `compact_boundary` with token counts and `turn_duration`. An `instructions` attachment carries the full loaded CLAUDE.md text, so a hash per session detects instruction changes. These field facts come from local inspection only, because Anthropic publishes no schema. The parser must therefore ignore unknown types and branch on field presence, never on version.

Two traps exist in the Claude Code data. The default `cleanupPeriodDays` is **30 days** ([Claude Code settings reference](https://code.claude.com/docs/en/settings-reference)), so most users have only one month of history. "Since the model's release" is often impossible on day one. The installer must tell the user to raise this value, and the script must keep its own compact store of derived metrics. Also, `CLAUDE_CONFIG_DIR` moves session history ([Claude Code settings](https://code.claude.com/docs/en/settings)), so the script must scan every config root. One API response also spans several JSONL lines with the same `message.id`, so the script must remove duplicates before it adds usage. Lines with model `<synthetic>` are harness placeholders and must not count.

Codex writes `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl` and has no automatic age-based deletion ([ghinda](https://allaboutcoding.ghinda.com/where-ai-coding-clis-store-session-logs/)). The first line is `session_meta` with `cli_version`. Each `turn_context` carries `model` and `effort`, and tool calls are flat `function_call` and `function_call_output` pairs linked by `call_id` ([openai/codex protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs); [MilkoorY](https://dev.to/milkoor/reverse-engineering-codex-cli-rollout-traces-3b9b)). The current persistence policy does **not** save `exec_command_end`, which holds `exit_code`, or `model_reroute` ([codex policy.rs](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/policy.rs)). The script must parse exit status from output text, and it cannot see a server-side model swap. The research found no real Codex files on the test machine, so the Codex parser needs tests on real files from several versions before release.

The packaging path is short. Claude Code installs plugins from a GitHub repo with `.claude-plugin/marketplace.json` through `claude plugin marketplace add owner/repo` and `claude plugin install` ([Claude Code docs](https://code.claude.com/docs/en/plugin-marketplaces)). Skills can bundle scripts that run through `${CLAUDE_SKILL_DIR}` ([Claude Code skills](https://code.claude.com/docs/en/skills)). Codex reads the same `SKILL.md` format from `.agents/skills` ([OpenAI skills](https://learn.chatgpt.com/docs/build-skills)) and installs plugins with `codex plugin marketplace add owner/repo` ([OpenAI plugins](https://developers.openai.com/plugins/build/plugins)). One repo with one shared skill and one stdlib Python script serves both CLIs with no build step. True "one line" means one shell line that runs both plugin commands, which is a small detail to confirm.

## Count friction you can see, and judge only what you cannot

The requested quality dimensions map to signals of very different reliability. Field research on real coding-agent sessions gives the base rates. SWE-chat studied about 18,000 sessions and found that users push back after about **46% of prompts** and hard-interrupt about **4.5% of turns**. Its pushback labels (correction, rejection, failure report, none) reached human agreement of κ = 0.83 to 0.89 ([SWE-chat](https://arxiv.org/pdf/2604.20779)). A study of 20,574 sessions found that **91.49%** of visible misalignment resolutions needed explicit user correction ([arXiv 2605.29442](https://arxiv.org/abs/2605.29442)). These rates were "relatively stable" across model releases from February to September 2026 ([SWE-chat](https://arxiv.org/pdf/2604.20779)). One metric that moves alone is therefore weak evidence. A real nerf shows as a coordinated shift in several signals inside the same user.

| User's question | Best signal | Type | Main confounder |
|---|---|---|---|
| Steering needed | Interrupts per task; corrections per task | Deterministic; LLM on flagged turns | Experienced users interrupt more (9% vs 5%) ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)) |
| Misunderstood a clear prompt | Correction where the violated requirement was stated earlier | LLM, blind, prompt rated before outcome | Vague prompts; "nitpicker" users |
| Buggy or uncompilable code | Tool `is_error` after edit; build/test fail after agent claims success; `userModified` edits | Deterministic | Language and task mix |
| Back-and-forth to finished work | User turns from first prompt to commit, PR link, or a new task | Deterministic with LLM task split | Task size |
| Silent effort drop | Output and thinking tokens per task; reads before edit | Deterministic | Thinking redaction and display changes |

The deterministic signals are the core of the tool. Tool-error rate, identical-call retries, failed edits, a build failure after the agent reports success, and search loops are hard to fake and depend little on user style. Failed SWE-bench trajectories are consistently longer and more variable than successful ones ([arXiv 2511.00197](https://arxiv.org/abs/2511.00197)), and search loops were the most stable anti-pattern across 2,500 trajectories ([TraceProbe](https://arxiv.org/abs/2607.06184)). Interrupt rate alone is weak, because Anthropic found that experienced users interrupt more often as they give more autonomy ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)). An LLM session-success score alone is also weak, because human-human agreement on it was only ICC 0.503 ([SWE-chat](https://arxiv.org/pdf/2604.20779)). Praise such as "thanks" is not a quality signal. The METR trial showed that developers felt about 20% faster while they were about 19% slower ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)).

The attribution rule for "misunderstanding when the prompt was clear" is the key fairness device. A correction counts against the model only when the violated requirement was already stated in the prompt, in CLAUDE.md, or in an earlier correction. A correction that adds new information ("also do X") is a scope change, not a model error. A repeated correction of the same point is strong evidence against the model. The judge must rate the prompt's clarity before it sees the agent's answer, so the outcome does not bias the clarity label. LLMs are weak at detecting ambiguity on their own ([CLAMBER](https://arxiv.org/pdf/2405.12063)), so the clarity label needs human validation like every other label.

Task segmentation has no validated standard for coding-agent transcripts. SWE-chat scores whole sessions and single prompts, not tasks ([SWE-chat](https://arxiv.org/pdf/2604.20779)). A simple rule set is enough to start: a new task begins at a non-correction prompt with a new intent, after a commit or PR followed by a new request, after `/clear`, or after a long idle gap. Correction prompts always attach to the current task. The strongest success proxy is a commit or PR link (Claude Code logs `pr-link` lines). The next is a test pass after the last edit with no later pushback, and the next is a new task without a correction.

## A frozen, blinded judge on flagged events keeps cost near zero

An LLM judge is necessary for corrections and clarity, but it adds its own drift. Judges show self-preference, leniency, and prompt sensitivity. Self-preference varied by model from +0.307 to −0.229 across 20 models, and 17 of 20 had a significant bias ([arXiv 2604.22891](https://arxiv.org/html/2604.22891v4)). Judges also preferred a text that was only labeled as their own ([Panickssery et al.](https://arxiv.org/pdf/2404.13076)). Judge severity changed significantly across all five version pairs in one audit ([arXiv 2608.29517](https://arxiv.org/abs/2608.29517)). The circularity risk is clear: if the judge comes from the provider under test, a change in the judge looks like a change in the product.

The fix is an anchor set. Li's "Who Drifted" method re-scores a fixed set of human-labeled items with the current judge on a schedule. Because the anchors never change, only judge drift can move their agreement with the human labels. The method caught a silent judge version change in 60 of 60 runs and attributed a prompt change correctly in 110 of 120 ([arXiv 2606.15474](https://arxiv.org/html/2606.15474)). For this tool, the anchor set is mandatory, because the cheapest judge is the user's own subscription through `claude -p` or `codex exec`, and the user cannot fully pin a snapshot there. If anchor agreement moves, the tool must say "judge drift" and must not give a nerf verdict.

The judge prompt follows established practice. It asks one narrow binary or small categorical question per field, because binary labels are harder to game and easier to validate ([Hamel Husain](https://hamelhusain.substack.com/p/llm-judge)). It puts reasoning before the label, which improved evaluator accuracy ([Eugene Yan](https://eugeneyan.com/writing/llm-evaluators/)). It requires an evidence quote, and the script rejects any label whose quote is not in the transcript. It removes dates, model names, version strings, the tool's name, and any user text about "nerfs", and it shuffles events across days. Majority vote over three samples improves agreement with humans ([arXiv 2606.26185](https://arxiv.org/html/2606.26185v1)), so the tool uses it for ambiguous events and anchors only. Validation needs about 30 labeled events per label to write the rubric and about 100 held-out events for a usable kappa ([Husain](https://hamelhusain.substack.com/p/llm-judge); [Cantor 1996](https://www.ime.usp.br/~abe/lista/pdfGSoh9GPIQN.pdf)). The tool must report Cohen's kappa, not percent agreement, because percent agreement overstated quality by 33 to 41 points on MT-Bench ([arXiv 2606.19544](https://arxiv.org/abs/2606.19544)).

Cost depends on what the judge reads. Haiku 4.5 costs $1/$5 per million input/output tokens, the Batch API gives 50% off, and cache reads cost 10% of input ([Claude pricing](https://platform.claude.com/docs/en/docs/about-claude/pricing)). If the judge reads only a window around each flagged event, with a cached rubric, the estimated cost is about **$0.0015 per event**, or about $1.50 per 1,000 events. Whole-session judging at about 100k tokens per session costs about $0.05 per session, and that difference becomes large at 100x volume. These per-event numbers are estimates, not measurements. Judge runs also write new transcripts into the same folders, so the script must tag and exclude its own sessions.

## Fixed windows, cluster bootstrap, and an equivalence test give a fair verdict

The noise floor sets the product promise. With a success rate near 60% and 20 tasks per day, the 95% interval is about **±21 points per day**. It is about ±10 points per week at 100 tasks and about ±5 points per month at 400 tasks. Clustering makes these intervals wider, because tasks in one session are correlated. On static benchmarks, clustered standard errors were up to **3.05 times** larger than naive ones ([Miller 2024](https://arxiv.org/html/2411.00640)). A daily score is mostly noise, so the HTML graph shows daily points only as faint dots behind a rolling 7-day and 28-day line with a 90% band. The tool never gives a verdict from one day.

The primary test is a fixed-window comparison. The baseline is a frozen reference period, for example the first 28 days of a model ID. The recent window is the last 7 or 28 days. The unit is the session, so missing days cause no problem. A cluster bootstrap that resamples whole sessions gives the interval for any score with no distribution assumption, and numpy runs 10,000 resamples in seconds. The windows must be fixed in advance, not started at the moment the user "felt" a change, because a window that starts after a bad stretch finds recovery by regression to the mean. Checking every day also inflates false alarms, so a "worse" verdict must hold on two consecutive weekly checks.

Confounder control uses the simplest method that works for each confounder. User workflow changes become **regime cuts**: a new CLAUDE.md hash, a new MCP or skill set, a new CLI version, or a new effort setting starts a new regime, and the tool compares only inside a regime or adds the regime as a covariate. Harder tasks and context growth become covariates: task type, prompt length, context tokens at start, compaction, files touched, and project. A logistic regression with session-clustered standard errors adjusts for them, with project as a fixed effect. A CUPED-style adjustment with the user's own baseline per-project rate removes project-mix drift; CUPED gives up to about 50% variance reduction in A/B testing ([optipilot](https://optipilot.com/data/cuped-variance-reduction)). The graph must show the within-stratum comparison next to the pooled number, because a move to harder projects can lower the pooled rate while every project stays flat. Full item response theory needs repeated items across many test-takers ([tinyBenchmarks](https://par.nsf.gov/servlets/purl/10547932)), so it fits only a canary set, not unique user tasks.

The verdict uses an equivalence test, which Marginlab does not do. The user sets a smallest effect of interest (SESOI), with a default of 5 points. TOST at α = 0.05 equals a 90% interval that lies fully inside the equivalence range ([Lakens](https://lakens.github.io/statistical_inferences/09-equivalencetest.html)), and the Bayesian HDI-plus-ROPE rule gives the same logic ([Kruschke](https://journals.sagepub.com/doi/10.1177/2515245918771304)). "No change" means the whole interval is inside ±5 points. "Slightly worse" means the interval is below 0 but not fully below −10. "Clearly worse" means the interval is below −5 and the estimate is −10 or lower. "Not enough data yet" covers every other case, and the tool shows how many more sessions it needs, from the power formula ([Miller 2024](https://arxiv.org/html/2411.00640)). One pre-declared primary metric drives the verdict, and the other metrics are descriptive diagnostics. If a composite is needed, the tool z-scores each metric against the baseline period and uses equal weights, which is the most common and most explainable choice ([OECD handbook](https://www.oecd.org/content/dam/oecd/en/publications/reports/2005/08/handbook-on-constructing-composite-indicators_g17a16e3/533411815016.pdf)).

Segmented regression adds value only at known event dates, such as a model release or a CLI upgrade, and it needs about 9 to 12 active days on each side ([BMC Med Res Methodol](https://bmcmedresmethodol.biomedcentral.com/articles/10.1186/s12874-019-0777-x)). Mann-Kendall gives false trends at n < 40 with autocorrelation ([Yue et al. 2002](https://agupubs.onlinelibrary.wiley.com/doi/10.1029/2001WR000861)), so it is not the verdict engine. A fixed canary set is the only clean separator of "the model changed" from "my work changed" ([Marginlab](https://marginlab.ai/trackers/claude-code/)). A personal canary of 20 tasks run 3 times still detects only drops of about 15 to 20 points, and its cost scales with users. A shared public canary is the better design, because one run serves every user.

## Open decisions to brainstorm before the first line of code

Several choices have no answer in the research and need a decision. The table names each one, the options, and the research-based lean.

| Decision | Options | Lean from the research |
|---|---|---|
| Primary verdict metric | Task success proxy; composite friction score; model-attributable corrections per task | One primary metric, chosen before the data is seen; the others are diagnostics |
| Judge provider | User's own CLI (`claude -p`, `codex exec`); cross-provider API; none in v1 | v1 deterministic only; v2 judge through the user's CLI plus a mandatory anchor set |
| Baseline definition | First N days of the model ID; rolling prior 28 days; cross-user baseline | Frozen first 28 days of the model ID; rolling baselines hide slow decay |
| History depth | Use existing logs only; ask the user to raise `cleanupPeriodDays`; keep a derived store | All three; the derived store is the only reliable long history |
| Task segmentation | Session = task; rule-based split; LLM split | Rule-based split first; validate on about 100 hand-labeled sessions |
| SESOI default | 5 points; user-set; per metric | 5 points by default, with one plain question to the user |
| Central brain | Fully local; opt-in upload of numeric aggregates keyed by model, version, effort, and date | Opt-in aggregates only; pooled data is the only way to separate "my work changed" from "the product changed" at scale |
| Thinking metrics | Include; exclude; include only inside a stable display regime | Only inside a regime, because redaction changes break them |

Some unknowns remain open. No study tests transcript metrics as detectors of silent model degradation. No source gives the intra-session correlation for real agent sessions, so the true width of the intervals is unknown until the tool measures it. The Codex parser has no real-file validation yet. The terms of use for automated judging through a subscription were not confirmed, and billing for `claude -p` changed during 2026 ([claudefa.st](https://claudefa.st/blog/guide/development/agent-sdk-credit)). Privacy is also a hard constraint. Transcripts are plaintext and contain CLAUDE.md text, file contents, git status, and the user's email ([ghinda](https://allaboutcoding.ghinda.com/where-ai-coding-clis-store-session-logs/)), so any upload must carry numbers only, with paths hashed or dropped.

## Conclusion

The product value is not the detection of nerfs. With one user's data, true detection is possible only for large drops. The value is a fair, explainable answer to "is it me or the model?". Most of the time the honest answer will be "no change" or "not enough data", together with a named user-side cause such as a new CLAUDE.md, a larger project, or a CLI upgrade. That answer is the "how did it know that?" moment, because no tracker and no vote can give it. The cost is almost zero, because deterministic counts do the work and the judge reads only flagged events. The design also inverts Anthropic's own blind spot: Anthropic could not read user conversations, and the user can.

The strongest long-term asset is the pooled, opt-in aggregate keyed by model ID, CLI version, effort, and date. One user can see only a 10-point drop. Thousands of users in the same regime can see a 2-point drop within days, and can show which CLI version or which slice of users it hit. That pooled view would have dated the 2025 routing bug and the 2026 effort change from real work, not from benchmarks. A v1 that ships only the local, deterministic verdict and collects regime-keyed aggregates is the simplest path toward that view.
